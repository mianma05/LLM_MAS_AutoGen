# LLM 辅助 PLC 代码生成与工业自动化编程：技术小报告（修订稿）

## 1. 问题定义

可编程逻辑控制器（PLC）是工业自动化的核心控制设备，其编程通常遵循 IEC 61131-3 标准，涵盖梯形图、结构化文本（ST）等语言 [S7][S10]。梯形图因可视化、贴近继电器控制逻辑，被认为降低了编程门槛并便于电气工程师与数字自动化衔接 [S7]。近年来，大语言模型（LLM）在通用代码生成上表现突出，研究者开始探索将其引入 PLC 编程：给定自然语言或结构化需求，由模型生成符合 IEC 61131-3 的代码，再通过验证与调试闭环提升可靠性 [S1][S10]。本报告面向本科生，回答三个问题：现有技术路线是什么、实证效果如何、距离工业落地还有哪些障碍。

## 2. 主要发现

**技术路线一：多 Agent 闭环生成与验证。** Agents4PLC 将任务拆分为检索、规划、编码、验证和调试五个 Agent，形成"生成—验证—修正"的闭环，强调生成结果必须经过验证环节才能交付 [S1]。这一思路借鉴了通用多智能体软件工程框架：MetaGPT 用角色分工和结构化产物组织协作 [S5]，AFlow 把 Agent 工作流表示为可搜索结构并利用执行反馈自动改进 [S2]，GPTSwarm 则将语言 Agent 建模为可组合、可优化的图 [S3]。对 PLC 场景而言，这些工作的启示是：单次生成不足以可信，流程编排与反馈迭代才是关键。

**技术路线二：面向 ST 的领域训练与在线反馈（待核实）。** 题录显示，有工作针对 IEC 61131-3 结构化文本训练 LLM，并使用在线反馈 [S10]；但检索结果未提供摘要，其具体方法、反馈形式与实际效果需核对原文后方可判断，本报告不据此下结论。

**技术路线三：形式化与结构化表示的支撑（据题名推断）。** 据题名推断，已有工作为 ST 提出面向过程的扩展语言 [S11]，采用基于文法的测试方法验证该扩展的实现 [S12]，并讨论 ST 代码在 IEC 61499 中的复用 [S13]。这些成果虽非 LLM 研究，但提示 PLC 语言具有严格语法约束，可为"生成后如何校验"提供文法与测试基础设施；具体内容需核对原文。此外，有工作探索用 LLM 生成信号时序逻辑以支持信息物理系统的故障检测 [S8]，说明 LLM 在工业场景中的角色可能不限于写代码，还包括生成可验证的规约（题录信息，细节待核实）。

**工具与生态。** Model Context Protocol 提供连接 AI 应用与外部数据源、工具的开放协议 [S4]，为 LLM 访问 PLC 工程环境、仿真器等外部资源提供了可能的集成方式。

## 3. 比较

从证据强度看，三类路线差异明显。多 Agent 闭环 [S1] 直接面向 PLC 代码生成，但为 2024 年预印本，缺少本报告可核实的评测数据；领域训练工作 [S10] 仅有题录，效果未知；通用 Agent 框架 [S2][S3][S5] 方法成熟但并非为工业控制设计，迁移效果需额外验证；文法测试与语言扩展 [S11][S12][S13] 提供的是验证手段而非生成能力，属于配套证据。背景资料方面，[S6] 为面向初学者的 Delta PLC 教材，[S7] 为讨论梯形图在工业控制中作用的 SSRN 短文，二者类型不同，均只能作为背景性材料，不能作为实证依据。总体而言，现有证据支持"LLM 可辅助生成 PLC 代码"，尚不足以支持"可替代工程师"。

## 4. 局限性

第一，评测证据薄弱：检索到的 PLC 生成工作多未提供可比的语法正确率、功能正确率或硬件在环测试结果 [S1][S10]，难以横向比较。第二，安全合规讨论缺失：功能安全标准、验证与确认要求、责任归属等落地关键问题在本次检索到的证据中几乎未被涉及，这既是现有文献的空白，也是本报告检索范围的局限。第三，多篇文献仅有题录信息 [S8][S10][S11][S12][S13]，相关描述只能标注为"据题名推断"或"待核实"。第四，教材与短文类资料 [S6][S7] 属背景性材料，证据等级较低。

## 5. 结论

LLM 辅助 PLC 编程已出现"多 Agent 闭环""领域训练""形式化校验配套"三条互补路线。其中，闭环验证的必要性有直接证据支持 [S1]；领域训练 [S10] 与文法测试、语言扩展 [S11][S12][S13] 可作为配套或待核实线索，尚不能支撑更强结论。对本科生而言，可将其理解为一条流水线：需求输入→模型生成 ST/梯形图→文法与仿真校验→反馈修正。当前研究仍处原型与辅助阶段，工业现场部署前还需补齐评测基准与安全合规论证。
