# LLM 辅助 PLC 代码生成与工业自动化编程：技术调研小报告（修订稿）

## 1. 问题定义

PLC（可编程逻辑控制器）是工业自动化的核心控制设备。据检索到的 CODESYS 教材条目与 TIA Portal 环境文献标题所示，PLC 编程涉及 IEC 61131-3 标准及 CODESYS、TIA Portal 等工程环境 [S8][S11]；但这些条目均无摘要，其具体内容有待核实，本报告不将其作为事实性依据。近年来，LLM 在通用代码生成上表现突出，研究者开始探索其能否用于 PLC 代码生成，以及如何嵌入“需求→设计→编码→测试→调试”的工程流程。本报告聚焦三个问题：现有 LLM 生成 PLC 代码的方法与能力边界；LLM 与工业编程流程及工具的集成方式；生成代码的安全性、可靠性与验证挑战。

## 2. 主要发现

**方法层面。** 现有工作最直接相关的证据是 Agents4PLC，它把 PLC 代码生成组织为“检索—规划—编码—验证—调试”的闭环，由多个 Agent 分工完成并迭代修正 [S2]。这一思路继承了通用多智能体软件工程框架：MetaGPT 用角色分工和结构化产物组织协作 [S1]，AutoGen 支持多智能体对话、工具调用与人工介入 [S3]，AFlow 把 Agent 工作流表示为可搜索结构并利用执行反馈自动改进 [S4]，GPTSwarm 则把语言 Agent 建模为可优化的图 [S6]。综述进一步从工作流、基础设施、通信和挑战等角度总结了 LLM 多智能体系统 [S5]。工具接入方面，MCP 是连接 AI 应用与外部数据源、资源和工具的开放协议 [S7]；将其类比用于工业工具链接入属于合理推断，并非 [S7] 原文结论。

**工程集成层面。** CODESYS 与 IEC 61131-3 的教材条目、TIA Portal 环境下的过程自动化文献，构成了 LLM 辅助编程可能对接的工具背景 [S8][S11]，但二者均无摘要，具体内容待核实。检索到的证据主要停留在“通用 Agent 框架 + PLC 专用闭环”的层面，尚未见到对具体 IDE 插件或产线级部署的详细描述。

**安全与验证层面。** 据标题与元数据，SIL 验证是工业控制代码相关的合规环节 [S12]；自动生成代码的安全论证可借助形式化程序验证信息来构建 [S13]；形式化验证生成代码在 DSP 代码生成系统 SPIRAL 上已有先例，用 Coq 证明生成规则与编译器的正确性 [S14]；针对 LLM 生成代码，已有工作在 Ada/SPARK 语境下开展软件验证 [S15]。上述条目均无摘要，结论仅据标题推断。

## 3. 比较

从技术路线看，Agents4PLC 与通用框架的差异在于其 PLC 专用验证闭环：它把验证与调试纳入生成过程 [S2]，而 MetaGPT、AutoGen 侧重通用协作与对话机制 [S1][S3]，AFlow、GPTSwarm 侧重工作流结构的自动优化 [S4][S6]。从验证强度看，形式化方法（如 Coq 证明 [S14]、Ada/SPARK 验证 [S15]）据标题推断提供最强保证，但成本高、覆盖面窄；SIL 验证 [S12] 与安全论证 [S13] 更贴近工业合规要求。总体而言，检索到的通用框架文献数量多于 PLC 专用文献，且 PLC 专用证据集中于单一系统 [S2]。

## 4. 局限性

本报告证据存在明显不足：Crossref 实时检索多次因 429 限流失败，PLC 方向仅获得 Agents4PLC 一篇直接文献 [S2]；CODESYS、TIA Portal 相关条目多为书籍或环境介绍，且部分元数据可疑（如标题高度相似、作者与年份不一致）[S8][S9][S10][S11]；SIL、形式化验证条目均无摘要，只能依据标题推断相关性 [S12][S13][S14][S15]。因此，关于语法正确性、可编译性、逻辑正确性的定量结论无法给出，工业界落地实践也缺乏证据。

## 5. 结论

LLM 辅助 PLC 编程目前最清晰的技术形态是“多 Agent 闭环生成 + 验证调试”，其方法论根植于通用多智能体框架 [S1][S2][S3][S4][S6]，工具接入可类比 MCP 等开放协议（属推断）[S7]。相关合规与验证文献表明，功能安全与形式化验证是需要重点关注的环节 [S12][S13][S14][S15]，且当前缺乏充分的实证评测。对本科生而言，可先了解 IEC 61131-3 与 CODESYS/TIA Portal 工程背景（相关条目待核实）[S8][S11]，再研究 Agent 闭环与验证反馈的设计。后续应补充近三年 PLC 专用论文与工业报告，建立可编译性与逻辑正确性的评测基准。
